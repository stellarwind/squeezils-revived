This guide explains the integration plan, the first full-build probe, and what

## 1. What is ready, and what the scoreboard means

The regenerated 2026-10-20 status reports 2,653 of 2,653 game-logic functions
with source: 2,248 byte-matched and 405 functional, with no todo functions.
The source manifest has 879 entries. An entry is a scoring unit, potentially
containing several source files, and the same file can occur in several entries.

That is enough to start integration. It does **not** establish that the entire
program already links or runs. Individual matching deliberately masks linker
relocations. A routine can have the right instructions and still name an
external function or global differently from the unit that defines it.

Three layers of evidence answer different questions:

| Check | What it establishes |
| --- | --- |
| Compile and compare one target | Its local instruction shape agrees with the original under the harness's comparison rules. |
| Link the whole program | Every retained external reference has a definition, with compatible linker symbols. |
| Run and exercise the game | Startup, shared state, resources, virtual dispatch, and gameplay cooperate correctly on the tested paths. |

Even a successful link cannot catch every mismatch between class declarations
in different translation units. Some layout and signature disagreements are
invisible to the linker.

## 2. The ingredients of the executable

| Ingredient | Existing location | Job |
| --- | --- | --- |
| Game code | `Repo/src/manifest.txt` and its sources | Application, rendering, simulation, UI, audio, and supporting classes. |
| Global data | `Repo/data/data.obj`, regenerated by `Repo/data/build.sh` | Strings, constants, globals, and pointer-bearing tables extracted from the user's original. |

| C/C++ runtime | Original compiler's `LIBC.LIB` | Startup, allocation, strings, math, exception/runtime support, and shutdown. |
| Import libraries | VC4 and DirectX 2 SDK libraries | References to functions supplied by Windows and DirectX DLLs. |
| Game assets | Existing game installation | Levels, models, images, sound, and configuration opened at runtime. |

The original imports d3drm, DDRAW, DSOUND, MSACM32, WINMM, KERNEL32, USER32,
GDI32, comdlg32, and ADVAPI32. Their import libraries are an initial dependency
list, not permission to replace the renderer or another subsystem.

An import library supplies the linker with information about a DLL export.
It does not contain the implementation of Direct3DRM or package its DLL into
our executable. Runtime dependency availability must be checked separately.

The probe uses the same default flags as the matcher:

```text
-GX -GR -Gy -O2 -G5 -ML
```

`-GX` enables C++ exception handling, `-GR` enables RTTI, `-Gy` packages
functions for linking, `-O2` enables optimization, `-G5` selects Pentium code
generation, and `-ML` selects the static single-threaded runtime.
Per-target `#FLAGS` settings take precedence. If the same source occurs under
the defaults and an explicit setting, the probe records the conflict and uses
the explicit setting once. Two incompatible explicit settings require review.
This is an integration choice, not a change to the scoring manifest.

The first probe can use the existing data/resource/QvLib binaries to diagnose
linkage. Their hashes are recorded, but they are explicitly **unverified cached
inputs**. A release-quality build must regenerate and validate them first:

```bash
bash Repo/data/build.sh
bash Repo/qvlib/build.sh
```

The data build can invoke Ghidra and requires the prerequisites documented in
`Repo/data/README.md`. Here, `data.obj` and `resources.res` exist but their
generated source, snapshot, and verification manifest are absent; their current
presence alone cannot establish freshness or correctness.

## 4. Compile the manifest into distinct object files

The probe reads the manifest, collects unique source paths, and compiles each
source exactly once with its selected flags. Every source gets a separate
numbered output directory. That prevents two unrelated files called `F.cpp`
from overwriting one another's `F.obj`.

`units.json` records the source, flags, object path, and compiler return code.
Each object directory contains its own `compile.log`. A nonzero compiler return
code or missing object is a real failure. The linker is skipped in that case;
linking a partial collection would obscure the first problem.

Do not simply compile every `.cpp` found recursively. The tree also contains
alternative matching units, helpers, and deliberate duplicates. The manifest
is the current starting inventory; integration will need a curated ownership
list as overlapping implementations are identified.

## 5. Ask the linker for an honest diagnostic

The driver writes `link.rsp`, a response file listing the options and inputs.
Response files avoid command-line length limits and make the exact attempted
link inspectable. The compiler's own `link.exe` is selected, not Git's unrelated
POSIX `link` utility.

The initial link requests an x86 Windows program, an output executable, and a
map file. It includes all compiled manifest objects, extracted data, resources,
QvLib, the static CRT, and the import libraries.

We leave entry-point selection to the Windows subsystem and VC runtime. The
runtime's WinMain startup performs initialization before calling WinMain.
Pointing `/ENTRY` straight at WinMain would bypass that machinery, including
important static initialization and runtime setup.

The driver does not use `/FORCE`, `/FORCE:MULTIPLE`, dummy function bodies,
zero-filled replacement globals, or hardcoded calls into the original image.
Such shortcuts could emit a file while concealing the very integration errors
we need to find.

The relevant outputs are:

| Output under `Repo/build/integration/` | Meaning |
| --- | --- |
| `summary.json` | Counts, compiler failures, link result, and cached input hashes. |
| `units.json` | Reproducible source-to-object inventory. |
| `flag-conflicts.json` | Different manifest flag sets encountered for one source, if any. |
| `duplicate-strong.json` | Ordinary external definitions occurring in multiple input objects. |
| `external-references.json` | Referenced external names not defined in the scanned loose objects. |
| `link.rsp` | Exact attempted linker inputs and options. |
| `link.log` | Actual linker diagnostics, or the reason linking was skipped. |
| `SQZ.exe`, `SQZ.map` | Useful only after a successful link; the map relates linked names to addresses. |

The pre-link symbol inventory does not search inside libraries. An external in
that report might legitimately be supplied by LIBC, QvLib, or an import library.
Use the actual linker diagnostics to identify unresolved symbols after library
resolution. Likewise, COMDAT and common-data repetitions are recorded differently
from ordinary duplicate strong definitions. COMDAT sections have selection
policies; some repetitions are illegal. Zero duplicate strong names is not a
promise of zero duplicate-definition linker errors.

## 6. Give every original function one implementation owner

The key integration identity is the original address, backed by disassembly and
the target mapping. Local spelling is not reliable: a function called
`Group::Traverse` in one reconstruction can be an implementation of a QvLib
method with a different class name and signature elsewhere.

Build an ownership table with: original address, target, defining source,
canonical decorated symbol, known aliases, and the evidence for the mapping.
Scoring targets use regexes and can deliberately map one generic implementation
to several original addresses, so this table cannot be derived by assuming a
one-to-one relationship between target lines and symbols.

For each collision, establish which case applies:

1. Two units reconstruct the **same original routine**: choose the canonical
   implementation and remove the redundant one from the integration inputs.
2. Different original routines happen to share a local class or function name:
   rename the local types/functions so both survive with distinct identities.
3. Two routines are intentionally equivalent helpers: sharing an implementation
   requires evidence that their addresses and side effects can safely coalesce.

Use `-Gy` and normal COMDAT handling where appropriate, but do not assume the
linker's willingness to fold/select a definition proves semantic equivalence.
Incompatible local class declarations can produce deceptively similar symbols.

The user has authorized renaming encountered during this integration. Prefer
shared headers and consistent declarations once identity is established. Keep
original-address comments so future byte-matching remains possible. Update any
affected target regexes and run the corresponding matching units after edits.

## 7. Resolve references with ABI evidence

Resolve missing references in categories: game methods, global data, QvLib,
compiler/runtime helpers, and Windows/DirectX imports. Work from the lowest
layer upward so repeated errors collapse together.

A C++ decorated name encodes class/namespace, parameter types, and calling
convention. A caller declaring `void *` and a definition declaring `Scene *`
can name different linker symbols despite both arguments occupying four bytes.
Conversely, agreeing names do not prove the same class layout in every unit.

Before merging names, check:

- `__thiscall` versus `__cdecl` versus `__stdcall`, including who removes arguments.
- Argument order, widths, return type, hidden structure-return arguments, and
  multiple-inheritance `this` adjustments.
- Object size, member offsets, base subobjects, and virtual-table slot order.
- The original destination address and the destination's actual behavior.

A link-time alias is appropriate only when these agree. It cannot repair a
wrong stack cleanup convention or a caller using the wrong member offset.
Do not automatically pair functions just because their names look alike.

## 8. Make shared data symbolic and singular

The data extractor emits 7,885 objects with 7,032 symbolic pointer relocations.
It deliberately skips some compiler-owned RTTI/vtables and library-owned data.
Its `function_targets.tsv` lists 5,859 code addresses, including internal EH
and jump labels. Those are not 5,859 ordinary standalone function definitions.

Build a data ownership map by original address, with type, size, initial value,
canonical symbol, and aliases. One original global must become one actual
storage location. If two units get independent copies of a counter, renderer
pointer, or singleton, the program can link and still behave incorrectly.

Bind each extracted pointer to its rebuilt destination and preserve offsets
into arrays, strings, and structures. Code pointers must reference new linked
code addresses. Original addresses remain useful metadata, not runtime targets.

Internal EH/jump targets require special care: an original offset inside a
function cannot be copied into a non-byte-exact replacement whose instructions
have moved. Compiler-generated exception metadata should follow its newly
compiled owner; other interior pointers need an explicit verified mapping or a
source-level reconstruction of the table they serve.

The extractor's coverage is not a whole-program data ownership proof. Regenerate
it, run its checker, and explicitly account for skipped globals and compiler
metadata. The checker verifies bytes/resources with symbolic relocation slots;
it does not verify that the final link chose the correct destination for every
pointer.

## 10. From linked file to tested game

After all compilation/link errors are resolved:

1. Verify the new file is a PE32 x86 executable with the intended subsystem,
   runtime startup, imports, and compiled resources. Inspect the map and import
   table. Check for unintended references back into the original game image.
2. Create an isolated runtime directory containing the rebuilt executable and
   the necessary local assets, configuration, and compatible dependencies.
   Preserve the original executable as the reference.
3. Inspect the existing `ddraw` proxy and compatibility configuration before
   including it: a proxy may contain hooks tied to original code addresses.
   A rebuilt layout invalidates those addresses even when behavior is correct.
4. Launch with the correct working directory. Record whether CRT initialization,
   WinMain, renderer creation, menu loading, and model import succeed. A crash
   before the window appears suggests a different layer than a crash loading a
   level. Use the map file and debugger to locate it.
5. Exercise menus, input, level loading, movement/collision, AI, inventory,
   animation, audio, save/load, and shutdown. Compare the same actions against
   the original with the same configuration and assets.

Keep claims tied to evidence: “links”, “opens the menu”, and “passes these
gameplay checks” are separate milestones. Mark `func!` only for functions whose
behavior has actually been checked, following WORKFLOW.md. Full gameplay
equivalence needs considerably more evidence than a successful launch.

1. Require each selected symbol to map to exactly its known original address,

2. Keep the owner's compiled definition. For incidental copies, turn the

## Integration workflow improvements (2026-10-21)

These requirements guide future integration work. The unified driver, freshness
validation, tracked decision registry, and expanded classification report below
are **not implemented yet**. Do not present them as available commands.

### 1. Make a clean run reproducible

The next tooling block should provide one driver that runs compilation,
ownership inventory, alias generation (data, entry, runtime, Qv), link-input
refresh, object projection, and diagnostic linking in dependency order. Split
the existing compile/link probe as needed so alias generation sees current
objects and the final link sees current aliases. Run once, read once; no polling
or automatic repair loop. Preserve failed compilation evidence and never omit
failed sources from a claimed complete build.

Validate freshness with hashes of sources and included headers, compiler and
flags/defines, manifest and target mappings, ownership/alias policies, libraries,
and generated inputs. File existence alone is insufficient. Reject stale or
missing prerequisites in verified mode; cached diagnostic mode must identify
unverified inputs. Record one run identity and input provenance in all reports.

Until that driver exists, use the manual sequence above, including the newer
runtime_aliases.py and qv_aliases.py generators before refreshing link inputs
and projecting them. Rebuild or regenerate dependent outputs after changes;
otherwise describe the result as a cached diagnostic.

### 2. Keep reviewed decisions separate from generated evidence

Create a tracked registry for reviewed mappings: original address, full
decorated symbol, implementation owner, aliases, ABI/layout evidence, and

### 3. Pick missing-definition families from classified evidence

references. For code pointers, classify exact entries, interior addresses, EH
